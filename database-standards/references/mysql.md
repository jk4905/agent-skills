## 适用范围

这个文件同时用于以下场景：

- MySQL 建表、改表、索引设计
- MySQL DDL 审批审核
- MySQL 5.7 / 8.0 兼容性检查

如果用户给了更细的规则，以用户最新规则为准。

## 审核总流程

1. 先识别语句类型：`CREATE TABLE`、`ALTER TABLE`、`DROP TABLE`、`TRUNCATE TABLE` 等。
2. 再判断目标版本：默认 MySQL 8.0，用户指定则按指定版本。
3. 先做语法和版本兼容性检查。
4. 再检查命名、字段类型、非空、默认值、注释、主键、唯一约束、索引。
5. 如果涉及索引新增或删除，结合 `table_info` 判断是否冗余。
6. 最后检查 DDL 风险：online DDL、锁表、`AFTER`、缩容改型、删除类操作。

## 设计审计重点

除了逐条检查字段、索引、类型、注释等硬规则外，还要优先从下面 5 个高价值审计点判断设计是否真正合理。目标不是只做机械查错，而是尽量在 AI 生成表结构阶段就把明显不合理的设计拦下来。

### 1. 访问路径审计

- 先看这张表未来会怎么查、怎么写、怎么排序、怎么关联，再决定字段和索引设计。
- 如果用户没有提供典型查询方式，应该主动提示这是信息缺失，不要让 AI 直接拍脑袋补索引。
- 对“先建很多索引，再假设查询场景”的做法保持警惕。

### 2. 业务唯一性审计

- 不只是检查“有没有唯一索引”，还要判断业务上真正的唯一约束是什么。
- 如果业务唯一性说不清，就不要随意拼多个字段上唯一键。
- 如果唯一性依赖多个长字段或文本字段，优先考虑生成列、摘要列等收敛方案，而不是直接堆超宽唯一索引。

### 3. 缩容变更审计

- 重点关注字段类型缩小、长度缩短、精度缩减、删除字段、删除索引等高风险 DDL。
- 例如 `bigint -> int`、`varchar(128) -> varchar(32)`、`decimal(18,2) -> decimal(10,2)` 这类变更，即使语法合法，也要优先提示兼容性风险。
- 这类场景默认需要更保守的判断，不应轻易给出“可以直接改”的结论。

### 4. 人工介入触发器

- 遇到以下场景时，应明确提醒需要人工确认：
  删除字段、删除索引、删表、截断表；
  缩容改型；
  唯一键字段过多；
  长文本直接建索引；
  索引数量明显偏多；
  核心查询字段放进 `json`；
  规则之间存在明显冲突或上下文不完整。
- 这类提示的目标不是阻止设计，而是避免 AI 直接产出“看似可用、实际上风险很高”的结果。

### 5. 样例查询反推审计

- 如果是建表或索引设计场景，应尽量从 2 到 3 条典型查询反推索引是否合理。
- 反过来说，如果索引设计无法对应到明确查询语句，就要警惕这是无效索引或过度设计。
- 对多字段联合索引，尤其要检查字段顺序是否真的匹配查询条件、排序条件和范围条件。

## 命名规范

- 数据库、表、字段、索引名称统一使用小写字母加下划线。
- 表名应体现 `业务模块_表用途`，例如 `order_payment`，不要使用 `t1`、`tmp_table` 之类弱语义命名。
- 列名要求见名知意，避免 `col1`、`field1`、`data` 这种无语义命名。
- 主键列统一命名为 `id`。
- 外键语义列命名为 `<实体>_id`，例如 `user_id`、`order_id`。
- 索引名称必须严格遵循：唯一索引以 `uk_` 开头，普通索引以 `idx_` 开头。
- 索引名称通常使用“前缀 + 字段名”形式即可，例如 `uk_mobile_phone`、`idx_user_id_status`。
- 索引名称中不要包含表名，避免名称冗长，正常情况下直接使用字段名组合即可。
- 如果索引字段较多，索引名称允许对后续字段做合理缩写，但前提是仍能识别业务含义。
- 索引名称长度不得超过 50 个字符。
- 所有对象名长度都应控制在 MySQL 64 字符限制内。
- 表名、字段名禁止与 MySQL 关键字或保留字重名，不接受反引号豁免。

## 建表基础要求

- 每张表都必须有主键。
- 自增主键类型不强制一律使用 `bigint`，应结合表数据规模和增长预期选择。
- 对于预估数据量在百万至千万级、且增长边界相对明确的表，主键优先使用 `int unsigned`。
- 对于预估仍会持续增长、未来可能超过千万级、或暂时无法明确上限的表，主键优先使用 `bigint unsigned`。
- 主键默认使用自增整型，常见写法为 `id int unsigned NOT NULL AUTO_INCREMENT PRIMARY KEY` 或 `id bigint unsigned NOT NULL AUTO_INCREMENT PRIMARY KEY`。
- 多表关联时，默认使用对方表的主键 `id` 作为关联字段来表达关系，例如 `user_id`、`order_id`。
- 不建议为了表关联再额外定义一套字符串类型的业务 ID 作为主关联字段；如果业务上确实存在订单号、外部单号、业务编码等字符串标识，也应将其视为业务字段，而不是替代主键关联关系。
- 表必须有表注释。
- 每个字段必须有字段注释。
- 默认引擎使用 `InnoDB`。
- 默认字符集使用 `utf8mb4`。
- 新表字段和索引都要有明确业务意义，不要预留“也许以后会用”的投机字段。

## 公司字段规范

- 除 `text` 和 `json` 外，所有字段都必须是 `NOT NULL`。
- `NOT NULL` 字段如果依赖默认写入路径，需要设置合理默认值。
- `created_at` 必须设置默认值。
- `updated_at` 必须设置默认值，并带自动更新时间。
- 涉及日期语义的字段，必须使用 `date`、`datetime`、`int` 或 `bigint`，禁止使用 `varchar`。
- 字段名是 `id`，或者本质上是整型业务 ID 的字段，必须使用 `int` 或 `bigint`，禁止使用 `varchar`。
- 商品品牌 id、垂类 id、品类 id 等小数据量业务字段，优先使用 `int`，不要使用 `bigint` 或 `varchar`。
- 如果字段注释语义是 `yyyyMMdd`，优先使用 `int` 或 `bigint`。
- 如果字段注释语义是 `yyyy-MM-dd`，优先使用 `date`。
- 注释要写清字段含义，必要时写出取值范围或编码说明。

## 数据类型规范

- 整数类型遵循“够用且最小”的原则，能用小类型就不要滥用大类型。
- 没有负数语义的整型字段，优先使用 `unsigned`。
- 单表自增主键如果规模可控在百万至千万级，没有必要默认使用 `bigint`，优先考虑 `int unsigned`。
- 用户 ID 字段务必使用 `bigint`；只有在用户标识本身存在特殊格式、且明确不是纯数值 ID 的场景下，才允许使用 `varchar`。
- 用户 ID、订单 ID、核心业务流水号等长期增长、跨系统流转、或明确会达到更大规模的标识字段，优先使用 `bigint`。
- 状态、类型、性别、年龄等枚举型或小范围字段，优先使用 `tinyint` 或 `smallint`。
- 金额、价格、费率等精度敏感字段，必须使用 `decimal(p,s)`，禁止使用 `float` 或 `double`。
- 国内手机号默认使用 `char(11)`；如果明确需要支持国际号码，使用 `varchar(20)`。
- 字符串长度要按业务实际设置，避免习惯性使用 `varchar(255)`。
- 长文本才使用 `text`；如果表很大，长文本字段要考虑垂直拆分。
- 时间字段使用 `datetime`，不要使用 `varchar` 存时间。
- 在当前团队口径下，不建议使用 `timestamp`；除非用户明确要求。
- 状态类字段优先用 `tinyint`，并在注释中说明枚举含义。
- `json` 只能用于扩展信息，不要把核心查询字段塞进 `json`。

## 索引规范

- 单表索引总数建议不超过 5 个；超过时要给出充分理由。
- 索引必须来自明确查询路径，而不是“可能以后会查”。
- 联合索引遵循最左前缀原则。
- 在允许的前提下，把区分度高的列放在联合索引前面。
- 如果查询里有明确的 `order by`、`group by` 路径，需要有针对性的联合索引设计。
- 一个索引中的字段数量不宜过多，通常不建议超过 3 个。字段越多，索引维护成本越高，查询命中和优化收益也更依赖于真实访问路径。
- 对于小表，尤其是数据量在 1 万行左右的表，通常可以少建索引甚至不建索引，优先保留唯一性最强、过滤性最强的字段即可。
- 如果是后端多字段混合查询场景，且底层使用阿里云 PolarDB，不要机械增加过多联合索引；可优先评估 PolarDB 列存索引方案。列存索引对多字段混合筛选场景通常更友好，在保证查询性能的同时，也能减少传统 B+Tree 组合索引数量和维护成本。
- 唯一索引字段数量不建议超过 3 个；超过时需要明确说明业务唯一性约束和收益是否足以覆盖维护成本。
- 索引命名必须严格执行 `uk_字段名` 和 `idx_字段名` 规则；字段较多时可缩写，但必须控制在 50 个字符以内。
- 索引命名禁止再带表名，避免 AI 生成类似 `idx_order_info_user_id_status` 这类冗长命名。
- 禁止冗余索引。如果已有 `idx_a_b`，一般不应再单独创建 `idx_a`。
- 禁止创建和主键重复的唯一索引。
- 禁止在其他二级索引、联合索引、唯一索引中再显式包含主键列。InnoDB 二级索引叶子节点默认已经包含主键值，再把主键列写进索引定义属于重复设计。
- 低基数字段如状态、性别，禁止单独建索引，除非和高选择性字段组成联合索引。
- `url` 字段或长度超过 100 的字段，不允许直接创建普通索引。
- 如果长字符串必须参与索引，优先考虑：
  新增 md5 辅助字段；或
  创建前缀索引，默认前缀长度不要超过 30。
- 如果 `url`、`task_key`、长编码、长业务串等长文本字段主要用于等值查询，优先考虑 MySQL 8.0 生成列方案：新增一个基于原字段计算出的 md5 生成列，再在该生成列上建立前缀索引。相比直接在长字段上建索引，这种方式通常能显著降低索引体积，并提升等值查询性能。
- 长文本等值查询优化示例：

```sql
ALTER TABLE `trd_sh_client_capture_task_info`
  ADD COLUMN `task_key_md5` varchar(32)
  GENERATED ALWAYS AS (MD5(`task_key`)) STORED COMMENT 'task_key md5虚拟列',
  ADD INDEX `idx_task_key_md5` (`task_key_md5`(15));
```

- 上述方案适用于“长字符串主要做等值匹配”的场景。先通过生成列持久化存储 md5 结果，再对 md5 字段建立前缀索引，通常取前 15 位即可满足大多数场景的性能要求。
- 如果唯一性依赖多个长文本字段或多个长字段组合，不建议直接建立超宽唯一索引；优先考虑通过 MySQL 8 生成列计算 md5 摘要，再基于摘要列建立唯一约束。
- 生成列方案示例：

```sql
ALTER TABLE `search_preview_keywords`
  MODIFY COLUMN `unique_md5` varchar(32)
  GENERATED ALWAYS AS (
    MD5(CONCAT_WS('#', task_id, grid_id, goods_id, style_id, keyword_type, keyword, is_deleted))
  ) STORED NOT NULL COMMENT '唯一ID';
```

- 上述场景中，推荐再基于 `unique_md5` 建立唯一索引，而不是直接对多个长字段拼装唯一键。
- 禁止使用外键，严格执行。

## DDL 变更规范

- 同一张表的多个 `ALTER TABLE` 操作，能合并就合并，避免重复锁表。
- MySQL 8.0 下新增字段时，避免使用 `ADD COLUMN ... AFTER ...`，以免影响 online DDL 能力。
- 新增字段优先追加到表尾。
- `varchar(32)` 改 `varchar(64)` 这类扩容变更通常更安全。
- `int` 改 `tinyint`、长字符串改短字符串这类缩容变更，必须明确提示兼容性风险。
- `DROP COLUMN`、`DROP INDEX`、`DROP TABLE`、`TRUNCATE TABLE` 都属于高风险操作。
- 对于删除类和缩容类操作，不要因为语法合法就直接给通过。

## 审核清单

- 语法是否符合目标 MySQL 版本。
- 命名是否全部小写下划线、语义是否清晰。
- 新表是否有主键、表注释、字段注释。
- 字段类型是否最小化、精准、符合业务语义。
- 日期字段是否错误使用了 `varchar`。
- ID 字段是否错误使用了 `varchar`。
- `created_at` 和 `updated_at` 是否符合团队规范。
- 非 `text` / `json` 字段是否都设置了 `NOT NULL`。
- 金额字段是否错误使用了 `float` / `double`。
- 索引数量是否超标，是否存在冗余索引、重复索引、低效索引。
- 单个索引字段是否过多，尤其是超过 3 个字段的联合索引是否真的必要。
- 小表（约 1 万行左右）是否存在不必要的过度索引设计。
- 后端多字段混合查询场景下，是否已经评估 PolarDB 列存索引方案，而不是继续堆叠过多联合索引。
- 是否在其他索引定义中显式包含主键列。
- 唯一索引字段数量是否过多，是否存在“多个长字段硬拼唯一键”的问题。
- 长字符串、`url` 是否被直接建索引。
- 长文本等值查询是否更适合改为 MySQL 8 生成列 + md5 前缀索引方案。
- 长文本组合唯一性是否更适合改为 MySQL 8 生成列 + md5 摘要方案。
- 是否存在 `AFTER`、缩容改型、删除类操作等高风险 DDL。

## 常见反模式

- 用 `varchar` 存 ID。
- 用 `varchar` 存日期。
- 用 `float` 或 `double` 存金额。
- 默认到处可空。
- 习惯性使用 `varchar(255)`。
- 新表一上来建超过 5 个索引。
- 单个索引字段太多，联合索引一路堆到 4 个及以上。
- 小表明明查询不重，却还在堆很多索引。
- 唯一索引一口气挂过多字段，导致索引过宽、维护成本过高。
- 多表本可通过主键 `id` 关联，却额外定义字符串类型标识来承担主关联关系。
- 在其他索引定义中重复包含主键列。
- 直接给长 URL 或超长字符串建索引。
- 长文本字段本质上只做等值查询，却仍然直接在原字段上建索引，而不是改成生成列 + md5 前缀索引。
- 多个长字段直接组成唯一键，而不通过生成列或摘要列收敛。
- 明明有联合索引，还继续补单列冗余索引。
- `updated_at` 没有自动更新时间。
