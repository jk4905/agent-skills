## 适用范围

这个文件用于 Redis key/value 设计、缓存设计、命令使用规范审核。Redis 不是 MySQL 风格的 DDL 系统，所以这里关注的是 key 命名、TTL、数据结构、命令安全和运行风险。

## Key 命名规范

- key 必须全部小写。
- 使用冒号分隔，示例：`shop:cart:user:12345`。
- key 要尽量短，但同时保持可读性。
- 推荐模式：`业务:实体:id[:子类型]`。
- 不允许使用特殊字符。
- 如果集群是共享的，需要带环境或租户前缀。
- 如果团队大量使用缩写，应维护一份统一前缀缩写表。
- 定义新的 key 家族时，必须给出示例 key。

## Value 设计规范

- `string` 类型建议控制在 10 KB 以内。
- `hash`、`list`、`set`、`zset` 的元素个数建议不要超过 5000，除非有明确例外说明。
- 数据结构要按访问模式选择：
  `string` 适合简单值；
  `hash` 适合小型结构化对象；
  `set` 适合成员判重；
  `zset` 适合排行榜和带分数排序场景。
- value 过大时，可以考虑 gzip 压缩。
- 禁止无边界地把大对象直接塞进 Redis，避免 bigkey。

## TTL 规范

- 大规模缓存数据必须设置 TTL，禁止默认永不过期。
- TTL 必须做打散，避免集中过期。
- TTL 不要随意设置过长，团队口径默认不要超过 30 天，除非有特别强的理由。
- 如果业务要求长期保留，应该重新评估是否更适合落 MySQL。

## 命令使用规范

- 只允许使用 db0，不要依赖非 0 逻辑库。
- O(N) 命令要谨慎，只有在 `N` 明确受控时才能接受。
- 遍历场景优先使用 `HSCAN`、`SSCAN`、`ZSCAN`，不要直接全量扫。
- 线上禁止使用 `KEYS`、`FLUSHALL`、`FLUSHDB`、`MONITOR`。
- 批量读取或写入优先考虑 `MGET`、`MSET` 或 pipeline。
- 批量操作要控制规模，默认建议 500 个以内，具体还要结合单元素大小判断。
- 不要滥用 `MULTI/EXEC`；大量非原子批处理更适合 pipeline。
- 不要把 Redis 当成通用大队列，长积压消息应使用 Kafka 等消息队列。

## 典型风险

- bigkey：会造成内存倾斜、慢操作、请求延迟上升。
- hotkey：会导致单分片 CPU 或带宽被打满。
- 热点 key 可以考虑本地缓存、只读副本、或 hash 打散。
- bitmap 场景要特别确认位偏移范围，避免位图过大导致内存失控。

## 审核清单

- Redis 是否真的适合这个场景，还是应该回到 MySQL。
- key 是否小写、冒号分隔、长度合理、语义明确。
- value 大小和集合元素数量是否有边界。
- TTL 是否存在、是否合理、是否做了打散。
- 是否使用了线上禁用命令。
- 是否严格使用 db0。
- 是否存在 bigkey 或 hotkey 风险。

## 常见反模式

- 把 Redis 当核心业务数据主库。
- 缓存 key 长期不过期。
- 超大 value 或超大集合没有拆分策略。
- 在线上使用 `KEYS`、`FLUSHALL`、`FLUSHDB`、`MONITOR`。
- 在集群模式里使用非 db0 逻辑库。
- 把 Redis 当成大消息堆积队列来用。
